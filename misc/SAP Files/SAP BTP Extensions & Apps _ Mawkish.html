Clean core, in plain words

Don't change SAP. Build next to it.

In older ERP systems, companies changed SAP's own code to fit their needs. Every upgrade then became a project, because someone had to check and repair every change. Many companies simply stopped upgrading.

Clean core means SAP's standard stays untouched. Your extensions connect only through interfaces SAP has released and promised to keep stable. SAP upgrades the core, and your extensions carry on working.

The old way

Modified core

Every upgrade means retesting and repairing custom code. Projects take months, so upgrades get delayed for years.

Clean core

Extended core

Before any of the three, we ask whether a standard process or setting already covers the need. Often it does.

Option 1 in practice

A new field in minutes, everywhere it's needed.

Say your sales team needs to record the tea grade on every sales order. A key user adds one custom field in the browser and chooses where it appears: the order screen, the invoice form, the sales report and the API that feeds your CRM.

Before promising any change, we check SAP's Extensibility Cockpit, which shows what each app and process allows. That way the answer is "yes, here's how" or "no, here's the alternative", not a surprise halfway through the project.

Agents are extensions too

Build your own AI agents, inside the same guardrails.

SAP's AI agents cover common tasks such as accruals and cash management. For tasks specific to your business, Joule Studio lets teams build custom agents by describing the outcome they want. SAP launched it at Sapphire 2026.

Custom agents run on SAP's managed platform, use the same business context as SAP's own agents, and act only within each user's existing permissions.

Describe, then refine

Joule Studio drafts requirements, logic and tests from a plain-language description. Developers can also work in Python or TypeScript.

Grounded in your SAP data

Agents use SAP's Knowledge Graph and business data, so they understand what an order, a supplier or a cost centre means.

Governed like any extension

Each agent has an owner, a clear scope, human approval where it matters, and a place in the regression tests.

Questions we hear

Straight answers.

Do we need to pay for SAP BTP?

Key-user changes and developer extensions inside SAP Cloud ERP come with your subscription, although developer extensions need the three-system landscape. Side-by-side apps run on SAP BTP services, which are subscribed separately and sized by use. We size this with you before you commit.

Will our extensions break when SAP upgrades?

Not if they're built on released interfaces, which is the only way SAP Cloud ERP allows. We also run each extension's tests on the upgraded test system before SAP upgrades production.

Our old ERP has hundreds of customisations. Do we rebuild them all?

Usually not. When we go through them, many turn out to be reports that standard analytics now covers, or workarounds for processes SAP now handles. The rest become key-user changes, developer extensions or side-by-side apps, and only where they still add value.

Low-code or pro-code?

Both have a place. Low-code with SAP Build is fast for forms, approvals and simple mobile apps. Pro-code with CAP or ABAP Cloud suits complex logic, high volumes and apps you'll grow over years. We choose per app and tell you why.

Can our own developers build extensions?

Yes, and we encourage it. Many clients have us build the first extensions together with their team, set the standards, and review what the team builds after that.

Who owns what we build?

You do. The code lives in your repository and runs in your SAP accounts, and the documentation is handed over with it.
